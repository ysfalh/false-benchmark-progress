Fast but False Progress on Benchmarks with Richer Feedback

Youssef Allouah John Duchi Sanmi Koyejo

Stanford University

Detailed benchmark scores help developers pinpoint the weaknesses of complex models. We show this feedback can accelerate ranking and score inflation on HELM1, LiveBench, Open LLM, SWE-bench, and Terminal-Bench-Science. In as few as 2 submissions, we manufacture a leaderboard winner that falls behind on unseen data. It is open whether past evidence of reliable ordinary benchmark reuse with scalar feedback holds with richer feedback.

0. Richer feedback

Benchmarks are a standard way to compare machine learning systems and guide model selection. For these comparisons to inform deployment, they must generalize: performance on the underlying test set should reflect performance on fresh data from the same population.

An aggregate benchmark score summarizes a model’s performance in one number. Many leaderboards also publish a separate score per criterion or task. We call this breakdown rich feedback.

This is an increasingly relevant type of evaluation in modern AI development. Indeed, general-purpose models can do many different tasks, and developers need to know where they work well and where they fail—a motivation behind benchmarks like HELM. A single aggregate can hide those differences and obscure what is being measured (Burnell et al., 2023; Jiang et al., 2026). This is especially relevant when test examples are private, as in ARC-AGI and other evaluations that use private data to reduce contamination risks.2 This creates the tension we focus on: evaluating more criteria gives developers a fuller picture, but returning more scores can also leak more information about the test set with each submission, making it easier to overfit through repeated use.

Based on the benchmarks we study below, each leaderboard submission receives the following scores:

  • HELM Capabilities (v1.15.0): the five task scores shown above.
  • HELM Lite (v1.13.0): ten scores, covering question answering, mathematics, and translation.
  • LiveBench (2024-10-22 snapshot): 18 task scores, including code completion, spatial reasoning, combining tables, and summarization.
  • Open LLM (v2): six task scores: IFEval, BBH, MATH Lvl 5, GPQA, MuSR, and MMLU-Pro.
  • SWE-bench Verified (2026-09-21 snapshot): ten repository-group scores reconstructed from released per-instance results. Repositories with fewer than ten instances are pooled.
  • Terminal-Bench-Science (v0.1): five domain scores reconstructed from released task outcomes: earth, engineering, life, mathematical, and physical sciences.

Every new submission returns another set of scores. Repeating this process on the same examples gives an attacker information that can be used to inflate apparent progress, in both scores and model selection. Our goal is to quantify the extent of this vulnerability using the modern benchmark data above. Note that the benchmarks above are not meant to be private and give per-item scores, so we instead simulate an interface where the attacker only sees task/criterion aggregates. The point is to show that, even without knowing the test set or anything about the benchmark in general, one can easily beat all other models in terms of aggregate score.

To approximate the performance on unseen data, we randomly split each benchmark into a reused set that returns leaderboard submission feedback and a held-out set reserved for evaluation. We then follow the reused-set ranking and scores before and after adding the attack, and compare the two choices on held-out data. We do so over 250 trials by default, over the randomness of the splits.

For starters, we will overview the main results quantifying the vulnerability, ignoring for the moment which attack allowed obtaining them.

1. Best-model selection

Does the best-ranked model hold up on unseen data?

We measure model selection loss: the held-out score of the model chosen before the attack minus that of the model chosen afterward. Positive values mean following the new ranking made selection worse.

Below, we observe that following the public ranking lowers held-out performance on all six benchmarks at 128 leaderboard submissions. In fact, in all cases, 16 submissions suffice to approach the 1 pp loss mark. The largest losses are on LiveBench and HELM Lite.

Each submission budget produces its own final attack model, so its held-out performance can improve as well as deteriorate. The dip for Terminal-Bench-Science reflects such an improvement; selection loss stays positive because the new choice still performs worse, on average, than the original public winner.

False winners and a counterexample

A false winner ranks first on the reused set but not on the held-out set. The curves below show the fraction of trials whose final attack model is a false winner, with additional curves requiring a held-out score at least 1, 2, or 5 pp below the best original model. This is the held-out score gap to the best original model; selection loss instead compares the public-selected models before and after the attack.

These rates describe the final model at each budget, so they need not keep rising. A model can remain first publicly while improving held out, so fewer trials exceed a score-gap threshold or count as false winners.

The first tested submission counts reaching a 90% false-winner rate are LiveBench, 4; HELM Capabilities, 16; HELM Lite, 64; Open LLM, 16; SWE-bench Verified, 2; Terminal-Bench-Science, 8. Intermediate counts were not tested. The false-winner rates and intervals include every tested budget.

A counterexample: Terminal-Bench

In an attempt to also replay Terminal-Bench 4.0, selection improves by 1.52 pp at 128 submissions, despite 77.2% false winners. This can happen as the original public winner need not be the best held-out model. Replacing it with a model between those two in held-out performance improves selection, even though the replacement is still a false winner. This illustrates why false-winner frequency alone does not measure selection harm.

The best-score generalization gap nevertheless exceeds its no-attack baseline. Improving the chosen model does not ensure that its public score is reliable: the best public and held-out scores can move farther apart while the selected model gets better. 2. Best-score generalization

Does the best score found through repeated submissions hold up on unseen data?

Now after each leaderboard submission, we compare the best score so far on the reused set with the best score so far on the held-out set. The largest absolute gap over this history is the score generalization gap. The two best scores may belong to different models. The baseline uses only the original benchmark models; it can be positive because their scores already differ between the two splits.

Below, we observe that the gap grows early on LiveBench and SWE-bench Verified, while HELM Lite and Open LLM continue to diverge with more submissions. Recall that these curves tell us how well the best reported score holds up; Figure 1 shows what happens to the model we choose.

Each budget ends with its own final attack model, so the final model from a shorter run is absent from the longer run’s history. The maximum is taken within each of these histories, so the plotted gap can decrease across budgets even though a running maximum cannot decrease within one run.

3. How the attack works

To keep things simple and to avoid running expensive model inferences, each attack leaderboard submission is a router: a rule that sends each prompt to one of two existing models. The attack uses public task scores from repeated submissions to choose which model handles each prompt. We illustrate the steps with one selected HELM Lite trial using 32 leaderboard submissions. The attack is mostly an adaptation of the boosting attack, which we discuss at the end of the section.

A. Choosing the two routing endpoints

The two models should be strong, but different enough that routing between them can help. We first remove models for which another model does at least as well on every task and better on at least one. Among the five highest-ranked models left, we choose the pair with the largest average absolute difference between their task scores.

In this example trial, that gives us A: Gemma 2 27B IT and B: DeepSeek V3. Before any new submissions, GPT-4o (August 2024) leads the public ranking.

B. Turning task scores into weights

Each submission is simply an independent random routing rule to choose model A or B for each prompt. Only a hash of the input/prompt is required to make the choice repeatable, so identical prompts always go to the same model. These rules are fixed before any feedback arrives. Each submission returns ten category scores in this example; two are shown below.

Weight = reference loss − candidate loss

(1)

A candidate that beats the reference gets a positive weight; a candidate that does worse gets a negative weight. The farther its loss is from the reference, the more its choices count. In the example, candidate 1’s LegalBench feedback gives weight -0.01426.

Combining many such scores strengthens the signal on the reused examples. For the reused LegalBench prompt with the smallest public hash, the weighted vote is +0.02201, so the final router chooses A.

The final router takes first place publicly but ranks fifth on the held-out split. Following it instead of GPT-4o lowers held-out performance from 74.10% to 70.14%, a 3.95 pp model-selection loss. This example illustrates the mechanism only; the earlier curves include every trial.

DeepSeek V3 has a slightly higher public mean score than GPT-4o in this figure, yet GPT-4o leads the original ranking. HELM Lite ranks models by their average win rate against other models within categories, which can order them differently from these mean scores.

Our work builds on the elegant line of research on adaptive data analysis, initiated by Dwork et al. (2015), discussed further in our previous paper. The attack draws on Blum and Hardt’s boosting construction (2015), Hardt’s generalized wacky boosting (2015), and the feedback-weighted aggregation of Feldman, Frostig, and Hardt (2019). Here, an important adaptation is that we select two strong models with contrasting strengths by maximizing task-profile separation among the top five models on the public Pareto frontier. We then combine random routers using public task scores, with the specific aim of studying how feedback richness accelerates overfitting and affects model selection across modern benchmark snapshots.

4. Controlling feedback richness

How much does richer feedback make the attack more efficient?

We want to understand how much the number of evaluation criteria accelerates the inflations we found. Consider LiveBench as an example where richer feedback brings selection harm fast. At 8 leaderboard submissions, mean selection loss is 1.43 pp with 1 returned score and 4.29 pp with 18.

We group the 18 LiveBench tasks into a varying number of super-categories, and return one average score per group, keeping the model pairs, random routing rules, and evaluation fixed. Each outcome is plotted against submissions and the total number of scores released.

Below to the right, indexing by the total number of released scores brings the curves quite close. This suggests that the amount of feedback---simply defined as the total number of unit measurements---helps explain how quickly the attack succeeds. By 128 submissions, mean loss is 4.59–4.85 pp across all six interfaces. Coarser feedback delays harm here, at the cost of hiding task differences that may matter for model selection.

Details of controlled comparison and extension to false-winner rates

The submission counts needed for a 90% false-winner rate show a 16× spread. The corresponding totals of released scores vary by only 1.5×.

We use the same splits, models, model pairs, and random routing rules throughout. We divide the 18 tasks into equal-sized groups, chosen without looking at scores, and release 1, 2, 3, 6, 9, or 18 group averages. The attack combines routing choices separately for each group. Model pairs are chosen using all 18 public task scores and stay fixed.

With one released score, all tasks are averaged equally. With six scores, the groups are chosen independently of the scores. Both differ from the historical interface, which grouped tasks by subject.

The one-score and 18-score interfaces are unchanged by regrouping, so their range bars collapse. This indicates agreement across groupings; uncertainty across benchmark splits remains.

Practical feedback policies: tasks, categories or one score

Now, let us think end-to-end about whether we can coarsen feedback to make it harder for the attacker to succeed. In particular, what if the attacker also has to choose its two models from the restricted feedback? A separate LiveBench comparison tests that question using 18 task scores, six natural category scores, or one overall score. The splits, seeds and submission budgets stay paired. Unlike the controlled study above, this changes both endpoint selection and the feedback used to build the router.

Returning only the overall score delays false winners here; six category scores offer no consistent improvement over task scores. Selection loss is half a percentage point better when releasing one aggregate score only. Yet, by 128 submissions, all three policies produce false winners in at least 99% of trials and lead to worse model selection. Thus, none establishes a safe policy. 5. Frequently asked questions

What information can the attacker see?

Only public task scores, task identity, and a stable prompt identifier are needed for routing. We use a prompt hash so identical prompts receive the same choice. Individual item inputs/prompts and scores remain hidden.

How do these attacks relate to ordinary model development?

This is an open question; these experiments measure vulnerability to deliberate attacks. Back in classical machine learning days, Roelofs et al. (2019) found little evidence of substantial overfitting across more than 100 Kaggle competitions. One explanation for reliable reuse is that developers mainly respond to clear improvements over the previous best, as in Blum and Hardt’s Ladder mechanism. Our accompanying theory paper shows fundamentally why this protection can weaken when models compete under different weightings of the criteria. Reassuring experience with scalar leaderboards therefore need not carry over to richer feedback.

The commercial stakes of LLM rankings also give developers incentives to game evaluation (Singh et al., 2025). Understanding how often the vulnerability studied here arises in ordinary development seems non-trivial, as we need to trace which criteria matter more in guiding later models and check whether the resulting gains persist on fresh data from the same population.

Can feedback counts predict vulnerability on another benchmark?

Not reliably. We tried on LiveBench and found that accounting for both released scores and reused examples aligns the score-gap curves well. But a fit learned there misestimates the submission count needed on the other benchmarks, so it cannot yet serve as a general vulnerability predictor. The prediction methods and results compare the fitted and observed thresholds.

Do repeated submissions add more than static task routing?

Yes. A static router sends every prompt in a task to the endpoint with the better public task score. It needs one submission and can improve on the original model choice. Repeated feedback lets the attack tailor routing to individual prompts. With 128 submissions, the attack leads to worse model choices on average than that one-submission control on every snapshot.

Can two non-leading models produce a false winner?

Yes. In a separate LiveBench test, we exclude every model tied for first on the reused set and choose the endpoints from the entire remaining Pareto frontier. The final router still becomes a false winner in 58% of 250 trials at 2,048 submissions. This shows that neither endpoint needs to start in first place. Recall that the false-winner rate counts ranking reversals; it does not tell us how often following the new ranking makes selection worse. What the saved results establish.

Does a larger score gap imply a worse selected model?

No, the two metrics answer different questions. For example, on HELM Capabilities, choosing endpoints from the top five gives a larger score generalization gap, while choosing from the entire Pareto frontier causes a larger loss in the held-out performance of the selected model.

6. Takeaways

  1. Stress-test your benchmark’s feedback interface. Run an adaptive attack using your benchmark’s scoring rules, released feedback, and realistic submission budgets. Keeping examples private does not prevent overfitting through repeated aggregate scores.

    To run our attack on your benchmark, connect its public scores and submission feedback through the adapter, or read the working example.

  2. Develop scaling laws for benchmark lifespan. A useful scaling law would relate test-set size, feedback richness, and differences among models to the number of submissions before score inflation or selection loss exceeds a chosen tolerance. Our initial score-gap predictor is a starting point, though it does not currently transfer reliably across benchmarks. Better predictions could help maintainers decide when to refresh their data or revise their feedback policy.

  3. It remains open whether ordinary development encounters this vulnerability. Our attacks leave open how often this happens in practice. Answering this may require tracing which comparisons guide later models and checking whether the resulting gains persist on fresh samples from the same population. If reuse remains reliable, are there properties of the model families or their use of feedback that explain why in rich-feedback setting?

    If reuse does not remain reliable in ordinary development, an open problem is to design feedback mechanisms that preserve utiltiy while controlling spurious progress at realistic data sizes and computational costs. Our previous paper's Frontier Ladder offers a starting point.
